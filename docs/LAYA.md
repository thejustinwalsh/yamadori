# Laya as a router: what was measured, what works, what does not

Measured 2026-09-22 against the live service on `http://127.0.0.1:1237`
(`convaiinnovations/laya`, 421M ModernBERT-large, pinned to the A4000).
Laya is **deterministic**: three identical calls returned identical
probabilities to six decimal places, so every number below is reproducible
rather than a sample.

Everything here is regenerated by:

```
python -X utf8 bench/laya_calibration.py                       # 3-way, binary cascade, distil
python -X utf8 bench/laya_calibration.py --route --orders 6 --tag ord6
python -X utf8 bench/test_laya_calibration.py                  # 46 runtime checks (44 assertion sites), no GPU
python -X utf8 bench/test_laya_calibration.py --live           # + 2 against the service
```

| artefact | what it is |
| --- | --- |
| `bench/laya_routing_labels.jsonl` | 59 labelled developer questions; 23 investigate / 23 answer_directly / 13 clarify. 10 carry `"hard": true` — an adversarial slice written to break surface cues. **Finding 5 reports that slice at n=9, not 10, and the missing one is not an error:** one of the ten hard items is labelled `clarify` ("Is ParticleField.tsx okay?"), and the binary "needs codebase?" question is scored only on the 46 non-`clarify` labels (23 + 23), so 9 of the 10 hard items are in scope and one is out. 37 cue-honest + 9 adversarial = 46. |
| `bench/laya_distil_labels.jsonl` | 29 labelled `(question, finding, paths)` triples; 17 grounded, 12 **fabricated** — confident, code-shaped prose citing files it does not describe. |
| `bench/laya_calibration.py` | the harness. Prints every table below. |
| `bench/test_laya_calibration.py` | every claim below as an assertion that fails when it stops being true. |
| `bench/data/laya_*_runs*.json` | raw per-item, per-ordering probabilities, so the tables replay with no GPU. |

Baselines used throughout, because "55%" is unreadable without them:

- **majority class**: always `answer_directly` → 39.0%
- **regex floor**: `rule_baseline()` in the harness, six lines, no GPU → 79.7%
  on the full 3-class set, 97% on the cue-honest slice, **0%** on the
  adversarial slice.

> **Two regex numbers circulate in this document and they do not conflict.**
> **79.7%** is Part I: the *same* `rule_baseline()` scored once over all 59
> labels of `laya_routing_labels.jsonl`. **0.841 ±0.023** is Part II
> (Finding 11): the *same* six lines, scored as the mean over 8 group-aware
> held-out splits of the **89**-label set (the 59 above plus the 30 in
> `laya_routing_labels_ext.jsonl`, none of which are marked `"hard"`).
> Different label set *and* different scoring protocol — whole-set accuracy
> versus mean held-out accuracy — so neither figure supersedes the other.
> Quote 79.7% against Part I tables and 0.841 against Part II tables, never
> across.

## VERDICT

**`route_in` as it ships today — a three-way choice over prose with a 0.3
margin gate — cannot be made usable.** It abstains on 91.5% of questions, and
when forced to answer it scores 50.8%, below the 79.7% a regex gets for free.
No gate value rescues it; the gate sweep is monotone downward in every column.

**One narrow configuration IS usable**: a *binary* "does answering this need
our source?" question, on a *prose* state, at a **margin gate of 0.30** —
95.5% accurate on the 47.8% of questions it decides. Its accuracy comes from
lexical cues, and it fails the same adversarial items the regex fails, so it
is worth shipping as a *cheap confirmation*, not as a *judgement*.

**The structured-state hypothesis is refuted.** It does not help; it actively
destroys the one question that works.

## Finding 1 — the shipped three-way `route_in` does not work

n=59, `mcp/shomen.py:route_in` reproduced exactly (same options, same
instructions, same 2-ordering average, same gate).

| variant | decided | abstention | acc \| decided | acc \| argmax (no gate) |
| --- | --- | --- | --- | --- |
| prose (what ships) | 5/59 | **91.5%** | 40.0% | **50.8%** |
| structured | 0/59 | 100.0% | n/a | 42.4% |
| hybrid | 7/59 | 88.1% | 42.9% | 47.5% |
| regex floor | 59/59 | 0% | 79.7% | 79.7% |
| majority | 59/59 | 0% | 39.0% | 39.0% |

Gate sweep, prose, coverage-accuracy (correct ÷ *all* items, so an abstention
counts as a miss — the number that matters when abstaining has a cost):

| gate | 0.00 | 0.05 | 0.10 | 0.20 | 0.30 | 0.40 |
| --- | --- | --- | --- | --- | --- | --- |
| decided | 59 | 47 | 37 | 16 | 5 | 2 |
| cov-acc | 50.8% | 40.7% | 33.9% | 11.9% | 3.4% | 1.7% |

Five-fold hold-out, gate chosen on the training folds: **every fold picks
gate 0.0**. There is no threshold worth having — the best achievable policy is
"never abstain", and that policy scores 50.8%.

Averaging over all six option orderings instead of two does **not** change it
(50.8% either way), so this is not a position-bias artefact.

**Solution.** Do not ship the three-way question. Delete `clarify` from Laya's
option set (Finding 3 explains why) and reduce the remaining decision to the
binary form in Finding 4. Concretely, in `mcp/shomen.py:route_in`: replace
the single `_choice_averaged` over three options with one `_choice_averaged`
over `{needs_the_codebase, general_knowledge}`, and handle underspecification
before Laya is called at all.

## Finding 2 — structured state does not help; it makes things worse

The hypothesis under test was: *Laya abstains because it is handed raw prose,
and becomes decisive when handed structured signals.* Three state forms, the
same 59 items, the same primitive, paired:

- **prose** — `route_in`'s current string.
- **structured** — signals only: `domains.detect()` tags, `discover.imports()`
  packages, `named_symbols()`, code-block flag, word counts, index size
  (7,742 chunks / 754 files), as a `key: value` block.
- **hybrid** — the signal block followed by the request text.

| | prose | structured | hybrid |
| --- | --- | --- | --- |
| 3-way argmax, 2 orders | **50.8%** | 42.4% | 47.5% |
| 3-way argmax, 6 orders | 50.8% | 39.0% | 57.6% |
| abstention at gate 0.3 | 91.5% | **100.0%** | 88.1% |
| binary "needs codebase?" | **82.6%** | 50.0% (chance) | 73.9% |

McNemar exact, paired, at gate 0.0: prose vs structured p=0.21–0.27, prose vs
hybrid p=0.21–0.81. **Nothing here is statistically significant at n=59** — but
the direction is consistently against the hypothesis, and the binary result is
unambiguous: structured state turns the working classifier into a constant
(`needs_the_codebase` on 59/59 items).

**Why.** Laya was trained to judge natural-language state. A `key: value`
block is out of distribution: it flattens toward a single answer and its
probability mass stops moving with the input. The signals themselves are not
worthless — the regex floor built from the *same* signals scores 79.7% — but
they are worth more to `if` statements than to a transformer.

**Solution.** Use the cheap signals directly in code, not as Laya input.
`mcp/domains.py:detect`, `mcp/discover.py:imports` and `named_symbols()`
already produce a 79.7% router for free and in microseconds. Keep prose as
Laya's state. The concrete change: nothing in `shomen.py` should stringify
signals into `state`; if signals are wanted, branch on them in Python and pass
prose to Laya.

## Finding 3 — Laya cannot detect underspecification, and says so confidently

`clarify` is chosen for only 2/13 clarify items (15.4%) in the three-way form.
Asked as a dedicated binary question — *"Is this request specific enough to
act on?"* — it is worse than that: it is a **constant**.

| variant | answer | fraction of items | mean margin |
| --- | --- | --- | --- |
| prose | `underspecified` | **59/59 = 100%** | 0.652 |
| structured | `underspecified` | 59/59 = 100% | 0.707 |
| hybrid | `underspecified` | 59/59 = 100% | 0.695 |

This is the single most important line in this document: **a margin of 0.65 on
a classifier with literally zero information.** `MARGIN_GATE` was introduced
to separate "decided" from "undecided". It does not. A large margin here means
the *option wordings* separate cleanly in Laya's embedding, not that the
*state* selected between them. Any code that reads `margin >= gate` as
"confident and therefore probably right" is reading a number that, for this
question, is 100% wrong 22% of the time with no warning.

**Solution.** Underspecification is not a Laya question. It is cheap and
deterministic: no concrete symbol, no code block, no file path, under ~8 words,
and a referring pronoun with no referent (`it`, `this`, `the other one`). The
`_CLARIFY_HINT` regex plus the `named_symbols()` emptiness test in
`bench/laya_calibration.py:rule_baseline` already gets 12/13 of these. Lift
that into `mcp/shomen.py` as a pre-Laya guard and return `clarify` from it
directly. **Blocker if you disagree:** none — this needs no model at all.

## Finding 4 — the one configuration that works

Ask a **binary** question, on a **prose** state:

```
instructions: "What does answering this request depend on?"
criteria:
  needs_the_codebase: "answering it requires reading this project's own source files"
  general_knowledge:  "answering it requires only knowledge of the language or
                       library, not this project's code"
```

Scored on the 46 non-`clarify` items (23 investigate / 23 answer_directly, so
chance is 50%):

| gate | decided | abstention | acc \| decided | cov-acc |
| --- | --- | --- | --- | --- |
| 0.00 | 46/46 | 0% | 82.6% | 82.6% |
| 0.10 | 37/46 | 19.6% | 86.5% | 69.6% |
| 0.20 | 32/46 | 30.4% | 87.5% | 60.9% |
| **0.30** | **22/46** | **52.2%** | **95.5%** | 45.7% |
| 0.40 | 12/46 | 73.9% | 100.0% | 26.1% |

On the cue-honest slice alone (n=37) it is a clean classifier: mean margin
0.338 when right, **0.017** when wrong — the margin genuinely separates, and
at gate 0.20 it is 27/37 decided at **100%**.

**RECOMMENDED MARGIN GATE: 0.30** for this question and this question only.
Recorded as `RECOMMENDED_GATE` in `bench/laya_calibration.py` and asserted in
`bench/test_laya_calibration.py`. It is *not* a gate for the three-way
question (no value works) and *not* for the distil questions (constants).

**Solution / how to ship it.** In `mcp/shomen.py`:

1. Pre-Laya deterministic guard returns `clarify` (Finding 3).
2. One `_choice_averaged` over the two options above, prose state, 2 orderings.
3. `margin >= 0.30` → `investigate` / `answer_directly`; below → abstain, which
   `route_in` already models correctly as `run=None`.
4. Keep `calibrated: False` off now — this *is* the calibration, so record
   `gate_source: "docs/LAYA.md finding 4, n=46"`.

## Finding 5 — the gate does not catch the case it exists for

10 of the 59 labels are adversarial: `investigate` questions stripped of every
repo marker ("Is the budget checked before or after the model call?"), and
`answer_directly` questions wearing decorative file paths ("If `src/main.rs`
has `fn main() -> Result<(), Box<dyn Error>>`, what does `?` do?").

**Why the table below says n=9 and the artefact table says 10.** The binary
"needs codebase?" question is a two-class question, so it is scored on the 46
non-`clarify` labels only. One of the ten `"hard": true` items is a `clarify`
("Is ParticleField.tsx okay?") and drops out with the other twelve. 5
`investigate` + 4 `answer_directly` = the 9 below; 37 cue-honest + 9
adversarial = 46. Nothing was excluded by hand.

Binary "needs codebase?", split by slice:

| | cue-honest (n=37) | adversarial (n=9) |
| --- | --- | --- |
| prose Laya | **36/37 = 97%** | **2/9 = 22%** |
| hybrid | 29/37 = 78% | 5/9 = 56% |
| structured | 18/37 = 49% | 5/9 = 56% |
| regex floor | 36/37 = 97% | **0/9 = 0%** |

And the margins invert. On cue-honest items: mean margin 0.338 right, 0.017
wrong. On adversarial items: **0.185 right, 0.208 wrong** — wrong answers carry
*larger* margins than right ones. At gate 0.20 the adversarial slice is 5/9
decided at 20% accuracy: confidently, unabstainingly wrong.

So the margin measures *"were the surface cues strong?"*, not *"am I right?"*.
Laya and the regex fail the same nine items, in the same direction, which is
the cleanest evidence available that Laya is doing lexical cue-matching here
rather than reading intent. (n=9 — this is a direction, not a rate.)

**Solution.** Two parts, and neither is a model change:

- *Bound the damage.* An `investigate` misfire costs one wasted search loop; an
  `answer_directly` misfire costs a wrong answer with no receipts. Make the
  policy asymmetric: abstain toward `investigate`, since investigating a
  general-knowledge question is cheap and the reverse is not.
- *Fix the blind spot properly.* The adversarial `investigate` items are exactly
  the ones a **corpus lookup** settles for free: "the retry helper", "the
  investigation loop", "the production renderer" are all resolvable against the
  7,742-chunk index. A one-shot `code_search` for the question's noun phrases,
  with "did anything in our index match?" as a boolean, would separate these
  nine without a model. **Blocker:** `mcp/code_search.py` is owned by another
  workstream right now, so this was measured but not wired in.

## Finding 6 — `distil`'s grounding question does NOT detect fabrication

This one was previously reported as strong (a grounded finding at margin 0.925
against a vague one at 0.070). **That was two data points and it does not
replicate.** At n=29, with fabrications written to be *code-shaped* rather than
*vague*:

| | value |
| --- | --- |
| chose `from_the_files` | **29/29 = 100%**, including all 12 fabrications |
| accuracy | 17/29 = 58.6% — exactly the base rate |
| mean margin | 0.867 (range 0.53–0.97) |
| mean p(from_the_files), grounded | 0.945 (min 0.886) |
| mean p(from_the_files), fabricated | 0.917 (max 0.985) |
| separation | **+0.029** |
| AUC | **0.667** (0.5 = nothing, 1.0 = perfect) |
| best single threshold | 69.0% at p ≥ 0.941 |

The earlier result was real but measured the wrong axis. A state-sensitivity
probe shows Laya *is* reading the input:

| state | p(from_the_files) |
| --- | --- |
| real grounded finding | 0.954 |
| real **fabricated** finding | 0.949 |
| empty string | 0.693 |
| unrelated prose (ferries in Oslo) | 0.391 |
| random characters | 0.386 |

So the question Laya answers is **"is this text about code and files?"** — for
which it works well — not **"does this text describe *these* files?"**. The
original 0.925-vs-0.070 pair differed on the first axis. Every finding a real
investigation produces sits on the same side of it.

This is the known weak regime, already documented in `mcp/shomen.py`:
Laya is weak when asked to compare content *across* passages. Grounding is a
cross-passage comparison in disguise — finding versus file list.

**Solution.** Do not ask Laya. `distil` already carries the right mechanism and
treats it as secondary: `out["cited_paths"]`, checked against what the tool
loop actually retrieved. Make that check **the** authority and delete the
grounding question, or replace it with a deterministic overlap test — do the
identifiers, line numbers and symbols in the finding actually occur in the text
of the cited chunks? That is a set intersection over data the investigation
already has in hand, costs nothing, and catches precisely the fabrications this
label set contains (every one invents specifics that are absent from the files
it names). **Blocker:** the overlap test needs the retrieved chunk *text*,
which `mcp/shomen.py:investigate` currently keeps in `_TRACES` but does not
hand to `distil`. Passing the trace handle into `distil` is a one-argument
change to a file another workstream owns.

## Finding 7 — `distil`'s verdict question is also near-constant

| | value |
| --- | --- |
| chose `answers_it` | 27/29 |
| argmax accuracy | 13/29 = 44.8% |
| at gate 0.3 | 19/29 decided, 57.9% accurate |
| collapsed to usable/off_target | 17/29 = 58.6% |

It calls 11 of the 12 fabrications `answers_it`, three of them at margins
above 0.7.
Same failure as Finding 6, same reason: judging a finding against a question
requires relating two passages.

**Solution.** Drop it. A verdict that says `answers_it` 93% of the time adds a
field to the response and no information, and its high margins make it look
trustworthy. If a verdict is wanted, it belongs to the model that wrote the
finding — ask the investigating context to end with "answered / partially
answered / could not answer" as a literal token, which costs one token of
generation and is grounded in what it actually did.

## The cross-cutting lesson

**Margin is not confidence.** Three separate questions here return large,
stable margins while carrying zero information (Findings 3, 6, 7), and the one
question that does work has margins that invert exactly where it fails
(Finding 5). The margin reflects how cleanly the *option wordings* separate,
plus how strongly the state's *surface features* match one of them. It reflects
correctness only when those two happen to coincide.

The practical rule that follows: **a margin gate is only meaningful after you
have shown, on labels, that the question is not degenerate.** The degeneracy
check — what fraction of items got the same answer — is printed by
`bench/laya_calibration.py --binary` and takes one line. Run it before
trusting any new Laya question, including ones added after this document.

## What is NOT claimed here

- That Laya is a bad model. It is a 421M classifier answering in ~23 ms and it
  is very good at "is this text about code" (Finding 6's probe). It is being
  asked cross-passage comparison questions it is documented to be weak at.
- That the adversarial slice is a rate. n=9. It establishes that the cue
  dependence exists, not how often it bites in production.
- That the binary question beats the regex. It does not — 97% vs 97% on the
  cue-honest slice, 22% vs 0% on the adversarial one. It is worth having as a
  second, independently-derived signal, not as a replacement.
- That the 59 labels are representative. They are hand-written by one person
  against this product's domains (three.js/TSL, R3F, TypeGPU, WGSL, Rust,
  TypeScript types, general programming). A label set written by someone else
  would move these numbers.

Added 2026-09-22 by the training workstream, appended to the measurement work
above rather than replacing it. Part I asked *can the shipped zero-shot
questions be made to work*. Part II asks *what happens if we stop prompting a
421M encoder and actually fit a head on our own labels*.

The two halves agree everywhere they overlap, which is worth stating because
they were measured independently with different harnesses: zero-shot `route_in`
is unusable (Part I: 50.8% when forced, 91.5% abstention; Part II: 52.9%

## Finding 8 — what Laya actually IS, from the code

Settled by reading `.venv-laya/Lib/site-packages/laya/common.py`, not inferred
from behaviour. `DecisionModel` is:

```
ModernBERT-large encoder
  -> + type_emb[qtype]                     (3 question types)
  -> 2-layer nn.TransformerEncoder "head"
  -> scorer: LayerNorm -> Linear(d,d) -> GELU -> Linear(d,1)
  -> act_head: Linear(d+4, 256) -> GELU -> Linear(256, n_act)
```

and `build_sequence` lays the input out as:

```
[CLS] <type> question: <instructions> [SEP] [MASK] opt0 [MASK] opt1 ... [SEP] <state> [SEP]
```

**It is an option-scoring cross-encoder, not a sentence encoder and not a
fixed-class classifier.** Every candidate answer is rendered into the input as
text and given its own `[MASK]` marker; `scorer` emits one scalar per marker;
a softmax over markers is the answer. `render_options` builds those option
strings, and `marker_pos`/`marker_mask` carry the positions through
`collate_items`.

Three consequences that decide everything else in Part II:

1. **The label space is open by construction.** That is exactly why arbitrary
   zero-shot questions work at all — and why the checkpoint has no particular
   competence at *our* boundary. Nothing in it has ever seen our labels.
2. **Abstention is not independent.** `act_head` consumes the pooled `[CLS]`
   concatenated with four scalars derived from the answer distribution itself
   (top-1 probability, top-1 minus top-2, normalised entropy, `k/255`). The
   `act_probability` the service returns is therefore a function of the same
   distribution the margin gate already looks at, not a second opinion.
3. **It is fully trainable.** The forward pass is differentiable end to end and
   `DecisionModel.forward` takes an explicit `detach_encoder` flag, so
   head-only training is a supported path. The package even ships the training
   utilities (`proper_reward`, `td_lambda_targets`, targets in
   `collate_items`). A full fine-tune is architecturally possible.

**Solution / what we did.** Full fine-tuning 421M parameters on ~89 labels
would memorise the label set, so the honest ceiling at this label count is a
light head on frozen features. `mcp/laya_head.py` extracts, from the *same*
forward pass the service already runs: the `k` marker logits, the pooled
post-head `[CLS]` (1024-d), the per-marker hidden states, and
`act_probability`. `scripts/train_laya.py` fits `softmax(Wx + b)` on those.
When the label count reaches four figures, revisit the full fine-tune — the
architecture supports it and this document should be updated when it is tried.

## Finding 9 — training fixes the abstention collapse, and the accuracy is real

89 labels (59 from Part I + 30 added here), 8 repeated group-aware holdout
splits, candidate and L2 and gate all chosen by cross-validation *inside* each
training split so the test side is never used to pick anything.

| route_in, held out | zero-shot | **trained** | majority |
| --- | --- | --- | --- |
| accuracy | 0.529 ±0.053 | **0.726 ±0.045** | 0.393 |
| abstention rate | 0.962 | **0.024** | — |
| accuracy when it answers | 1.000 (on 3.8% of items) | 0.74 (on 97.6%) | — |
| ECE | 0.123 | 0.240 | — |
| median top-two margin | 0.058 | 0.893 | — |

The zero-shot "1.000 accuracy when it answers" is not a win: it answered 3.8%
of questions. **A gate that abstains 96% of the time has not made a decision,
it has deferred one** — which is precisely the System-2 call the head exists to
avoid. The trained head decides 97.6% of them at 74%.

The winning configuration is `logistic_cls` — a plain multinomial logistic
regression on the frozen pooled `[CLS]`, cross-validated at 0.808. The
`markers` and `vector_scale` features lose to it; `temperature` alone sits at
0.515, i.e. chance, which is the expected result and the point of Finding 10.

ECE gets **worse** (0.123 → 0.240) and that is not a bug: the zero-shot model
is well calibrated about being uncertain, because it is uniformly uncertain.
The trained head is confident and right 74% of the time, which is a more useful
and less well-calibrated object. Temperature-scale the shipped head if
calibrated probabilities matter more than decisions; `vector_scale` reaches ECE
0.052 at lower accuracy if that trade is wanted.

## Finding 10 — why the previous calibration work could never have worked

`index/calibration.json`, from `scripts/calibrate_laya.py`, records
`temperature 9.95, ece 0.279 -> 0.032, accuracy 0.5066`. That file is an honest
measurement of a technique that **cannot** do the job:

**Temperature scaling is monotonic.** Dividing every logit by one scalar cannot
reorder them, so the argmax is identical before and after and accuracy is
mathematically unchanged. `calibrate_laya.py` even asserts this and warns if it
moves. It makes confidence honest; it cannot create capability. The fitted
temperature hitting 9.95 — essentially the top of the search range, flattening
everything toward uniform — is the model saying "my confidence is meaningless",
not "I have been fixed".

**Solution.** Any head with more than one parameter can reorder. The cheapest
is `vector_scale`: a full `k×k` affine map on the marker logits, which can
correct a systematic preference for one option (k²+k = 12 parameters for a
3-way choice). It reaches 0.673 on `route_in` where temperature reaches 0.515.
`logistic_cls` goes further at 0.808 because it is not confined to the k
numbers the prompt already produced. Both are in the candidate list and are
selected by measurement, so this mistake cannot recur silently.

## Finding 11 — the trained head LOSES to a six-line regex

This is the result that decides whether any of the above should ship, and it
would have been missed by comparing only against zero-shot.

`rule_baseline()` from `bench/laya_calibration.py`, scored on the **same
held-out splits** as the trained head rather than quoted from a different
label set:

| route_in, held out | accuracy | adversarial slice |
| --- | --- | --- |
| zero-shot Laya | 0.529 ±0.053 | 0.333 |
| **trained Laya head** | 0.726 ±0.045 | 0.271 |
| **regex, no model, ~1 ms** | **0.841 ±0.023** | **0.000** |
| majority class | 0.393 | — |

**0.841, not 79.7%, and both are right.** Part I quotes the same six-line
`rule_baseline()` at **79.7%**, scored once across all 59 labels. This table is
the mean over 8 group-aware held-out splits of the 89-label set (59 + the 30 in
`laya_routing_labels_ext.jsonl`). Different labels, different protocol; the
regex did not improve, it was scored differently and on easier extra items.
Only the 0.841 row is comparable to the head's 0.726, because those are the
splits the head was evaluated on.

Training buys +0.197 over zero-shot and still loses by 0.115 to a regex that
needs no GPU, no service and no labels. Both numbers are true and the second
one is the one that matters for a shipping decision.

The adversarial slice (Part I's `"hard": true` items, ~3 per split) is where
this gets interesting rather than simply embarrassing: the regex scores
**0.000** there by construction, because those items were written to defeat
surface cues. The trained head scores 0.271 — better than zero, worse than
zero-shot's 0.333, and on n≈3 per split all three are within noise of each
other. **No configuration tested handles the adversarial slice.** The head does
not rescue it, and claiming it as the head's justification would be reading
noise.

**Solution, and it is not "ship the head".** Route with the regex. It is more
accurate, free, and already written. Keep the trained head served alongside it
as a second, independently-derived signal for the cases the regex is known to
be blind to — but treat "they disagree" as a reason to escalate to System 2,
not as a reason to trust either one. To make the head worth more than that it
needs either far more labels (hundreds, not 89, at which point the full
fine-tune the architecture supports becomes the right move) or features the
regex cannot see; the adversarial slice is the benchmark it has to move, and
today it does not move it.

**This is enforced in code, not left to memory.** `scripts/train_laya.py`
scores the regex on every split and records the comparison in the artefact;
`mcp/laya_service.py:beats_rule_baseline()` reads it back and `GET /heads`
reports `"beats_rule_baseline": false` plus an explicit note for `route_in`.
`bench/test_laya_head.py` asserts that note exists. A future retrain that
overtakes the regex will flip the flag automatically.

## Finding 12 — grounding without the file in the input is unlearnable

Part I established that the grounding question does not detect fabrication.
Part II establishes *why*, which determines whether it is fixable.

The grounding labels split into two kinds of negative, and pooling them hides
everything:

| sub-task (24 positives, cross-validated) | best accuracy | majority |
| --- | --- | --- |
| grounded vs **generic advice** (12) | **0.814** | 0.667 |
| grounded vs **fabricated specifics** (12) | 0.645 | 0.667 |

Generic advice is detectable from surface form — "you should", "is important",
"in general" — and needs no knowledge of the cited file. Fabricated specifics
are **not decidable from the input at all**: `"MAX_TRACES is 256"` and
`"MAX_TRACES is 1024"` are the same sentence to any classifier that cannot see
`shomen.py`. The state named the file and never showed it.

**This is a data design fault, not a model limitation.** No amount of training
recovers information that was never in the input, and any accuracy above
chance on that sub-task would have been the model exploiting a labelling tic.

**Solution, measured.** Put the file in the state and the question becomes
entailment rather than recall. `bench/make_grounded_excerpts.py` generates 30
matched pairs — one supported finding and one contradicted finding over the
*same* real excerpt, pulled live from real files so they cannot drift — and
both members of a pair are forced onto the same side of every split, because
they differ only in the claim.

## Finding 13 — the excerpt alone does not fix it; the excerpt must be cancelled

Supplying the excerpt was necessary and **not sufficient**. The first trained
run on excerpt-bearing data scored 0.544, below its 0.500 baseline in places
and no better than zero-shot. The reason, measured on standardised pooled
`[CLS]` vectors:

| cosine between | value |
| --- | --- |
| the two members of a pair (same excerpt, opposite label) | **0.727** |
| two unrelated examples | −0.015 |

The ~1100-character excerpt dominates the representation; the ~20-word finding
that determines the label barely moves it. A linear head cannot separate two
points that are nearly the same point.

(Measured on *standardised* vectors deliberately. Raw `[CLS]` cosine is 0.9998
within a pair — and 0.9993 between unrelated examples, because the raw space is
strongly anisotropic. The raw number looks alarming and means nothing; it was
checked and discarded before drawing any conclusion, and is recorded here so
nobody re-derives the wrong version.)

**Solution, measured.** Run the excerpt *alone* through the same stack and
subtract:

```
delta = cls(finding + excerpt) - cls(excerpt alone)
```

The shared component cancels and what remains is what the finding contributed.
`render_base_state()` in `mcp/laya_head.py` produces the contrast state and the
`delta_cls` / `delta_cls_logits` feature specs consume it, at the cost of one
extra forward pass per decision.

| grounded_excerpt, held out | zero-shot | trained | majority |
| --- | --- | --- | --- |
| accuracy | 0.570 ±0.037 | **0.625 ±0.099** | 0.500 |
| abstention | 0.715 | 0.042 | — |

**Verdict: still not shippable.** 0.625 ±0.099 on 60 labels is about one
standard deviation above chance, the winning configuration changes from seed to
seed (a sign that selection is fitting noise), and a grounding gate that is
wrong a third of the time is worse than no gate because it launders
fabrications as verified. The contrast trick is a real effect worth keeping —
it is the only thing that moved the number at all — but the honest read is that
grounding needs either several hundred labels or Part I's deterministic overlap
test.

**Part I's solution is the better one and both halves independently reached
it**: check the identifiers in the finding against the text of the retrieved
chunks. That is a set intersection over data the investigation already holds,
costs nothing, and cannot hallucinate. Blocker is unchanged — it needs the
chunk text handed to `distil`, in a file another workstream owns.

## What did NOT work — the negative results, kept on purpose

Every one of these cost real time. They are listed so the fourth Laya
investigation does not pay for them again.

| tried | result | why |
| --- | --- | --- |
| Temperature scaling to fix accuracy | 0.507, chance | Monotonic; cannot reorder an argmax. Finding 10. |
| `markers` features (per-option hidden states, k×1024) | 0.679 vs 0.808 for `cls` | 3× the parameters on 89 labels; overfits. |
| `vector_scale` on the k logits | 0.673 | Confined to the k numbers the prompt already produced. Best ECE though (0.052). |
| `centroid_cls` (nearest centroid) | 0.699 | Assumes equal isotropic classes; `clarify` is not shaped like the other two. |
| Grounding with filenames but no file content | ≤ chance | Information absent from the input. Finding 12. |
| Grounding with excerpts, plain `cls` features | 0.544 | Excerpt dominates the representation. Finding 13. |
| Raw `[CLS]` cosine as a similarity diagnostic | 0.999 for *everything* | Space is anisotropic; must centre first. Finding 13. |
| Single 70/30 split for reporting | moved 0.826 → 0.731 on a reseed | ~25 test items; one split is noise. Now 8 repeats with error bars. |
| Selecting the candidate on the test split | inflates by ~0.08 | Selection bias. Now nested: CV inside train only. |
| Beating the regex | 0.726 vs 0.841 | Finding 11. The one that decides the shipping call. |

Two methodology faults are worth calling out separately because they produced
*wrong numbers that looked fine*, not obvious failures:

- **Pair leakage.** Both members of a grounding pair share an excerpt. Split
  them across train and test and a head that memorised one has effectively seen
  the other. `stratified_split` and `kfold` are group-aware now; grouping is
  keyed on the `pair` field and `bench/make_grounded_excerpts.py` emits it.
- **fp16 batch non-determinism.** Padding a batch changes the fp16 reduction
  order, which perturbs the logits and hidden states slightly. Harmless for a
  zero-shot argmax; not harmless for a linear head fitted on one version and
  served the other. Features are extracted at **batch size 1** in both trainer
  and server for that reason.

## RUNBOOK — adding labels and retraining

**1. Add labels.** Append to any file matching the task's glob; new files are
picked up automatically, so create your own rather than editing someone else's.

| task | glob | required fields |
| --- | --- | --- |
| `route_in` | `bench/laya_routing_labels*.jsonl` | `question`, `context`, `label` in investigate / answer_directly / clarify |
| `grounded_excerpt` | `bench/laya_grounded_excerpt_labels*.jsonl` | `finding`, `cites`, `excerpt`, `label` in grounded / generic, plus `pair` if two rows share an excerpt |

Mark cue-resistant items `"hard": true` — that slice is reported separately and
is the benchmark that actually needs to move. For generated grounding pairs,
add a case to `CASES` in `bench/make_grounded_excerpts.py` and regenerate;
excerpts are pulled from live source, so a renamed function fails loudly
instead of silently emitting a stale excerpt.

**2. Retrain.**

```
.venv-laya/Scripts/python.exe scripts/train_laya.py --task all
```

Only new label *states* are sent through the model; everything else is served
from `index/laya/features_<task>.json`. Use `--no-cache` after changing a
prompt (and bump `PROMPT_REV` in `mcp/laya_head.py`, which invalidates the
cache and makes the server refuse stale artefacts).

**3. Check it got better.** Read the printed summary:

- `accuracy` must beat `majority baseline`, or the head learned nothing.
- `RULE (regex, no model)` — if it still wins, **do not promote the head**.
- `ADVERSARIAL slice` — the number that has to move for the head to be worth
  more than a second opinion.
- Watch for the selected candidate changing between seeds; that means
  selection is fitting noise and the label set is too small to conclude from.

Then run the tests, which enforce the floors in `bench/laya_baseline.json`:

```
.venv-laya/Scripts/python.exe bench/test_laya_head.py --serve
```

A retrain that scores below a floor **fails here rather than shipping**. If the
new numbers are genuinely better, raise the bar deliberately:

```
.venv-laya/Scripts/python.exe bench/test_laya_head.py --update-baseline
git add bench/laya_baseline.json index/laya/*.json
```

**4. Serve it.** The service loads every artefact in `index/laya/` at startup.

```
POST /route {"task": "route_in", "question": "...", "context": "...",
             "engine": "auto" | "trained" | "zero_shot" | "both"}
GET  /heads      what is loaded, what it scored, which engine is default
```

`auto` picks by the artefact's own recorded held-out numbers, so a head that
did not beat zero-shot can never become the default by accident. Restart the
service to pick up a new artefact. Test on an alternate port — never take down
1237:

```
LAYA_HTTP_PORT=1299 .venv-laya/Scripts/python.exe mcp/laya_service.py
```

**5. Roll back.** Artefacts are self-contained JSON and nothing else depends on
them:

```
git checkout HEAD~1 -- index/laya/route_in.json     # previous head
rm index/laya/route_in.json                         # or drop to zero-shot entirely
```

Removing the file makes `/route` fall back to the zero-shot engine and `/heads`
report `loaded: false`. `/decide` is untouched by any of this.

## Verdict for Part II

**`route_in` — usable as a gate, but it should not be the gate.** Training
takes it from 0.529 at 96% abstention to 0.726 at 2% abstention, which is a
real and reproducible improvement over zero-shot and resolves the abstention
collapse. It nevertheless loses to a six-line regex (0.841) on the same splits,
and neither handles the adversarial slice. Route with the regex; keep the head
as a cheap second signal and escalate disagreements to System 2.

**`grounded` — not usable, and the reason is now precisely located.** Without
the file in the input the decision is undecidable (Finding 12). With the file
in the input it is decidable but the representation is swamped by the excerpt
(Finding 13); cancelling that with a contrast pass recovers real signal and
still only reaches 0.625 ±0.099 on 60 labels. Use Part I's deterministic
identifier-overlap check instead. The pipeline for this task is left in place
and passing so that adding labels is the only work needed to re-test it.

**What is genuinely new and worth keeping** is not either accuracy number: it
is that `scripts/train_laya.py` now measures all four contenders — zero-shot,
trained head, regex, majority — on the same splits with error bars, records the
comparison inside the artefact, and fails the build if a retrain regresses. The
previous two Laya investigations produced numbers. This one produces something
that re-runs.
