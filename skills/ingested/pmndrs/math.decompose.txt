# Math Tuples and Out Arguments
- DO: treat every math type (Vec3, Quat, Mat4 ...) as a plain fixed-length tuple of numbers: no classes, no wrappers, no typed arrays.
  source: "Every type is a plain fixed-length tuple of numbers — no classes, no wrappers, and not a typed array"
- DO: pass the out argument first and return it for composite results; scalars and booleans are returned directly.
  source: "**`out` first, return `out`** for composite results: `fn(out: Vec3, a: Vec3, b: Vec3): Vec3`. Scalars and booleans return directly."
- WHEN the same array can arrive as out and as an input, as in vec3.normalize(v, v) or vec3.cross(a, a, b): read every input component into a local before the first write to out.
  source: "Read every input component into a local before the first write to `out`, so a write can't clobber an input still needed."
- DO: keep long-lived state as plain data the caller allocates once and owns; functions receive it, mutate it in place and return it.
  source: "Long-lived state is plain data the caller allocates and owns. Functions receive it, mutate it in place, and return it."
- DO: preallocate arrays to capacity when the state is created; when full, return a count or status instead of growing inside a hot loop.
  source: "Preallocate flat or typed arrays to capacity. When full, return a count, sentinel, or status rather than growing inside a hot loop."
- DO: compose the math primitives (vec3, mat4, quat) and the math/shapes, math/geometry, math/noise, math/random and math/time subpaths.
  source: "**Compose `math` primitives** (`vec3`, `mat4`, `quat`, and the `math/shapes`, `math/geometry`, `math/noise`, `math/random`, `math/time` subpaths)."

phases: implement, debug, review

# Math Hot-Path Pitfalls
- WHEN code is recursive, nested or runs in a worker: pass it caller-owned workspace; module-level scratch variables are not reentrant.
  source: "Module-level scratch variables are not reentrant. Pass caller-owned workspace for recursive, nested, or worker code."
- WHEN comparing distances: compare squared distances with squaredLength / squaredDistance instead of their square-rooted pairs.
  source: "Compare squared distances; reach for `squaredLength` / `squaredDistance` over their square-rooted pairs."
- DO: choose each tolerance for its operation and scale, and say why; one epsilon does not fit every operation.
  source: "One epsilon does not fit every operation or scale. Choose each tolerance and say why."
- DO: define what happens for empty input, zero-length vectors, degenerate geometry, NaN and exact boundary contact.
  source: "Define behavior for empty input, zero-length vectors, degenerate geometry, NaN, and exact boundary contact."
- WHEN choosing between a plain array and a typed array such as Float32Array: choose the typed array for interop or memory, not for speed; a packed plain array is already unboxed.
  source: "Don't assume a typed array is faster. A packed plain array is already unboxed and can still grow."
- DO: build each state object with the same keys in the same order every time, with no optional fields and no keys added later.
  source: "Build the object with the same keys in the same order every time. No optional fields, no keys added later."

section: Working with other libs / three.js
name: math-with-three-js
description: Use when TypeScript that uses the npm `math` package (pmndrs/math) exchanges vectors, quaternions or matrices with three.js objects, or fills GPU buffers such as an instanced attribute.
phases: implement, debug
topics: toArray, fromArray, vec3.fromBuffer, vec3.toBuffer, vec3.create, Float32Array
# Math With three.js and Buffers
- DO: marshal in, compute, marshal out: keep scratch math values at module scope (const _orbit_position = vec3.create()), fill them from the other library's values, run plain math calls, then write the results back.
  source: "Keep the scratch `math` types at module scope, fill them from the other library's values, run the algorithm as plain `math` calls, then write the results back."
- DO: move three.js Vector3, Quaternion, Matrix4 and Euler values through toArray(target) and fromArray(source); the component order matches math's.
  source: "`Vector3`, `Quaternion`, `Matrix4`, and `Euler` all marshal through `toArray(target)` and `fromArray(source)`, and the component order matches `math`'s in every case."
- DO: always pass your scratch array to toArray; called without a target it allocates a fresh array.
  source: "Always pass your scratch to `toArray` — called bare, it allocates a fresh array."
- WHEN filling an instanced attribute or a packed particle array: use vec3.fromBuffer(out, buffer, i * 3) and vec3.toBuffer(buffer, v, i * 3), or buffer.set(m, i * 16) for a whole matrix.
  source: "that's `vec3.fromBuffer(out, buffer, i * 3)` and `vec3.toBuffer(buffer, v, i * 3)` (also on `vec2`, `vec4`, `quat`), or `buffer.set(m, i * 16)` for a whole matrix"
- DO NOT: pass a Float32Array where a Vec3 is expected; marshal across the boundary instead.
  source: "**A `Float32Array` is not a `Vec3`.** The tuple types don't accept one, and casting past that gets you a value the rest of the codebase can't rely on."
- WHEN a camera orbits a target: keep its state as a Spherical plus a target the caller owns, and give three.js only the resulting position.
  source: "The camera's state is a `Spherical` and a target the caller owns; three only ever sees the resulting position."
