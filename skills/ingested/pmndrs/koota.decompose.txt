# Koota Traits and Entities
- DO: define data as traits: schema traits for plain primitive data (trait({ x: 0 })), callback traits for complex objects or instances (trait(() => new Thing())), and tags (trait()) for flags.
  source: "**Trait** - A reusable data definition. Can be schema-based (SoA), callback-based (AoS), or a tag."
- DO: name tags with an Is prefix (IsPlayer, IsEnemy), relations with a preposition (ChildOf) and data traits with a noun (Position).
  source: "| **Tags**      | Start with `Is` | `IsPlayer`, `IsEnemy`, `IsDead`  |"
- DO: create one world with createWorld() and spawn entities from it with their traits: world.spawn(Position({ x: 100, y: 50 }), Velocity, IsPlayer).
  source: "Entities are unique identifiers that compose traits. Spawned from a world."
- DO: change an entity through entity.set, add, remove and destroy; entity.set(Position, { x: 10 }) writes and triggers change events.
  source: "entity.set(Position, { x: 10 }) // Write (triggers change events)"
- WHEN a callback (AoS) trait's object is mutated directly: signal it with entity.changed(Trait) so hooks see the change.
  source: "For AoS traits where you mutate objects directly, manually signal with `entity.changed(Trait)`."
- DO: type what entity.get returns with TraitRecord<typeof Position>.
  source: "Use `TraitRecord` to get the type that `entity.get()` returns"

# Koota Queries and Systems
- DO: batch-update entities with world.query(Position, Velocity).updateEach(([pos, vel]) => ...) rather than for...of with entity.get().
  source: "Prefer `updateEach`/`readEach` over `for...of` + `entity.get()` for data-bearing queries."
- WHEN a query mixes tags or Not() with data traits: destructure only the data-bearing traits in updateEach / readEach; tags, Not() and relation filters are left out of the tuple.
  source: "**Note:** `updateEach`/`readEach` only return data-bearing traits (SoA/AoS). Tags, `Not()`, and relation filters are **excluded**:"
- DO: use readEach for read-only iteration; it passes the entity as its second argument.
  source: "`readEach` still gives you the entity as the second argument."
- DO: take a single match with world.queryFirst(IsPlayer, Position), and filter with modifiers: Not(Velocity) excludes a trait, Or(IsPlayer, IsEnemy) matches either.
  source: "world.query(Position, Not(Velocity)) // Has Position but not Velocity"
- DO: write each system as a small single-purpose function of the world (applyVelocity(world), applyGravity(world)) so it can be switched off on its own.
  source: "Design systems as small, single-purpose units rather than monolithic functions that do everything in sequence."
- DO: keep behavior out of the data: traits hold data, entities compose traits, and systems change the data through queries.
  source: "Behavior is separated from data. Data is defined as traits, entities compose traits, and systems mutate data on traits via queries."

# Koota With React
- DO: import core types (World, Entity) from 'koota' and the React hooks (WorldProvider, useQuery, useTrait) from 'koota/react'.
  source: "**Imports:** Core types (`World`, `Entity`) from `'koota'`. React hooks from `'koota/react'`."
- WHEN a hook such as useTrait does not rerender: change the trait through entity.set() or world.set(), which trigger the change events the hooks listen to.
  source: "`entity.set()` and `world.set()` trigger change events that cause hooks like `useTrait` to rerender."
- DO: keep the core (traits, systems, actions, world) in plain TypeScript with no view imports; the view reads the world and changes it through actions.
  source: "**Core** - Pure TypeScript. Traits, systems, actions, world. No view imports."
- DO: use traits for data and actions for behavior instead of classes; keep classes for objects an external library requires, such as three.js objects.
  source: "Only use classes when required by external libraries (e.g., THREE.js objects) or the user prefers it."
- DO: run the logic independently of rendering, so the view can be swapped or the logic moved to a worker.
  source: "- Run logic independent of rendering"
